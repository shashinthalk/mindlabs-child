# Child Theme Guidelines — Compatibility Contract with the Parent Theme

This file documents the **contract** between this child theme
(`hexnity-wp-child`, `Template: hex-wp-theme-template`) and its parent
theme (Hexnity WP AI Theme, folder `hex-wp-theme-template`). It exists
because this child theme does not generate its own documentation from
scratch — it inherits a large, actively-evolving design-token system
from the parent, and breaking that contract (wrong units, a
hand-edited reserved key, a missing header) causes silent, hard-to-diagnose
drift rather than a clean error.

**Anyone or anything modifying this child theme — human or AI — must
read this file first and follow it.** These are not suggestions; they
are the boundaries that keep this child theme working with the parent
at all.

These are **instructions/guidelines only**. This file does not attempt
to document the parent theme's internals in full — for that, read the
parent's own `claude.md`, `features/design-system.md`, and `knoladge/`
folder directly (`../hex-wp-theme-template/`). What follows is
specifically the subset that constrains *this child theme's* changes.

## 1. Required `style.css` header — do not remove or rename

```
Template: hex-wp-theme-template
```

This is what makes WordPress treat this as a child theme of the
parent at all, and it's also what the parent's own child-theme
installer (`inc/child-theme.php` in the parent) checks before ever
installing/updating this theme from GitHub — it fetches this file's
`Template:` header and confirms it matches the parent's own slug
before proceeding. Never change this value, and never delete the
header.

## 2. Enqueue architecture — don't re-enqueue the parent's stylesheet

The parent's own `functions.php` enqueues its compiled Tailwind build
(`assets/css/tailwind.css`, registered as the `hex-tailwind` handle)
on every request, **regardless of whether the parent or this child
theme is the active theme**. This child's `functions.php` does not
need to (and should not) re-enqueue it.

If this child theme adds its own stylesheet, declare `hex-tailwind` as
an explicit dependency (as `functions.php` already does for
`hexnity-wp-child-style`) so load order stays correct even if the
parent's own enqueue setup changes later — never assume a load order
based on file position or timing.

## 3. `theme-options.css` — the most important compatibility surface

This file (`theme-options.css`, this child theme's own directory) is
where every one of the parent's ~187 Theme Options fields actually
lives. It is **not optional infrastructure** — the parent's
`hex_enqueue_child_theme_tokens()` enqueues it directly when this
child theme is active, and every front-end design token flows through
it.

- **Format**: a single `:root { --hex-{key}: {value}; }` block.
  Regenerated in full by the parent's Theme Options admin page on
  every save. You can also hand-edit it directly.
- **Every length value must be `px` — never `rem`, `em`, or `%`.**
  The sanitizer technically still accepts those units (for backward
  compatibility with older saved files), but the parent's own schema
  defaults and every fallback in its compiled CSS are 100% `px` as of
  this writing. Mixing units here causes real, hard-to-spot drift —
  see the parent's `knoladge/fluid-typography-clamp.md` for the full
  story of a session that had to hunt down 73 stray `rem`/`em` values
  across this exact file. Always add new values in `px`.
- **Derived/reserved keys — never hand-set these independently.** For
  every text-size family (`h1`–`h6`, `body`, `lead`, `large`, `small`,
  `meta`), the key `--hex-{key}-size` (no `-mobile`/`-desktop` suffix)
  is **always** auto-regenerated by the parent as a flat copy of
  `--hex-{key}-size-desktop` on every Theme Options save — never a
  `clamp()`, never independently editable. If you hand-set
  `--hex-h1-size` to something different from `--hex-h1-size-desktop`,
  the next admin save silently overwrites it back into sync. Edit
  `--hex-h1-size-desktop` (and `-mobile`, which currently has no
  consumer but is preserved for a future/child use) instead — never
  the derived key.
- **Adding your own custom token is supported and safe.** Any
  `--hex-*` property in this file that the parent's schema doesn't
  already know about is auto-detected on the next Theme Options page
  load as an editable "Custom Tokens" field (type guessed from the
  value's shape: color/length/number/font/custom). Reference it from
  your own CSS as `var(--hex-your-key, fallback)`. If you're not sure
  a name is safe from a future parent-schema collision, prefix it
  distinctly (e.g. `--hex-child-*`).
- **Never delete this file.** If it's missing, the parent's enqueue
  function silently no-ops — the site still renders (every token has
  its own CSS-level fallback in the parent's compiled CSS), but every
  saved customization is gone and nothing will tell you why sizes
  look like the parent's raw defaults again.

## 4. The design-system classes live in the PARENT theme — this theme only keeps a reference copy

Superseded again (2026-08-29, reversing the 2026-08-28 move described
below): `.hex-h1`…`.hex-meta`, `.text-h1`…`.text-h6`, `.btn`/`.btn-*`,
`.card`, `.form-control`, `.alert`, `.badge`, `.table-styled`,
`.nav-menu`/`.nav-link`, `.accordion`/`.accordion-item`,
`.tabs`/`.tabs-input`/`.tabs-label`/`.tabs-panel`, `.icon`, and the
bare `h1`–`h6`/`a`/`body`/`.prose` overrides are **built and enqueued
by the parent theme only** — `hex-wp-theme-template/assets/css/src/site-theme.css`,
compiled to `hex-wp-theme-template/assets/css/tailwind.css` via the
parent's own `npm run build:css`, enqueued by the parent's own
`inc/enqueue.php` (`hex-tailwind` handle, loaded via
`get_template_directory_uri()`, which always resolves to the parent
regardless of which child theme is active). **This is the correct,
intended place to edit them — not this child theme.**

*(2026-08-28 history, now reversed)*: these classes briefly lived
here instead, with this child theme running its own independent
Tailwind build (own `package.json`, own `front.css`, own compiled
`assets/css/tailwind.css`, own enqueue). Explicit user correction the
next day: *"before u added tailwind css to child theme. thats wrong.
it should be in main theme and should load via main theme."* That
build tooling (`package.json`, `package-lock.json`, `node_modules/`,
`assets/css/src/front.css`, `assets/css/tailwind.css`) has been
removed from this child theme, and its Tailwind enqueue removed from
`functions.php`.

This child theme still keeps `assets/css/src/site-theme.css` on disk
as an **editable reference/starting-point copy only** — editing it has
**no effect on the live site** unless you copy your changes into the
parent theme's own `assets/css/src/site-theme.css` and rebuild there
(`npm run build:css` in the parent theme's own folder). **The parent
theme, with no child theme active, again has full design-system
component styling** — it is self-sufficient.

If you do extend the parent's copy, follow the same two hard rules
already baked into `.hex-*`'s fluid clamp(): (1) exactly one shared
`clamp()` calculation for every fluid class — never duplicate the
formula per class, add new classes to the existing shared selector
list instead; (2) the fluid breakpoints
(`--hex-static-breakpoint-s/-m/-l/-xl`) are hardcoded plain `:root`
values, never sourced from `theme-options.css` / admin-editable — keep
it that way for any new fluid class you add.

See the parent's `features/design-system.md` ("Where the CSS classes
actually live now") for the full current reference, and
`knoladge/child-theme-css-token-architecture.md` there for the
detailed history of both the move and its reversal.

## 5. This child theme has its own, fully independent updater

Configured on the parent dashboard's separate "Child Theme" admin
page — its own GitHub repo/branch/token options
(`hex_child_github_repo`/`hex_child_github_branch`/`hex_child_activation_key`),
its own settings group (`hex_child_updates`), its own update-checker
instance and transient log, completely isolated from the main theme's
own "Updates" page and its settings. Don't assume the main theme's
updater configuration applies here, and don't wire this child theme's
functions.php into the main theme's updater option names — the parent
theme's own `claude.md` treats this isolation as a hard rule ("if
main-theme has an update, only the main theme is checked/installed;
if the child theme has an update, only the child theme is").

## 6. Versioning

Bump both together on any real change to this child theme:

- `style.css`'s `Version:` header
- `functions.php`'s `HEXNITY_WP_CHILD_VERSION` constant

(Mirrors the parent theme's own versioning discipline — see its
`claude.md`.)

## 7. Folder boundary — the mirror image of the parent's own rule

The parent theme's `claude.md` confines an AI session working *on the
parent* to the parent's own directory. The same principle applies in
reverse here: a session working on *this child theme* should confine
its reads/writes/edits to this child theme's own directory. If a
genuinely parent-side change is needed for compatibility (a new
reserved key, a renamed enqueue handle, a schema change this child
theme now depends on), that's a change for a session explicitly
scoped to the parent theme — not something to patch from inside this
child theme's directory, and not something to assume is safe to guess
at without reading the parent's own current source.
